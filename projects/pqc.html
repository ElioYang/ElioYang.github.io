Measuring the Cost of Post-Quantum Migration

A testbed I built to measure what post-quantum key exchange actually costs on telemetry links, starting with a bias I found in my own first version. First-place undergraduate paper, ITC 2026.

Question

What does moving a telemetry link to post-quantum key exchange cost in practice, and under which conditions does that cost appear?

What I did

  • Built a Ground Station–Test Article testbed comparing classical ECDH, ML-KEM at three security levels, and three hybrid configurations, measuring latency, CPU time, memory, and bytes on the wire.
  • Found that my first version ran classical and post-quantum schemes through different software libraries, which made an implementation cost look like an algorithm cost. I rebuilt it so that every scheme runs through the same TLS 1.3 stack.
  • Swept bandwidth, round-trip time, and concurrent load instead of reporting a single benchmark on an idle link.
  • With two co-authors, built an adaptive selector that uses a contextual-bandit policy to choose among operator-approved post-quantum configurations as link conditions change (ITC 2026).

Result

In the single-client baseline, ECDH and ML-KEM-512 differ by less than 2% (28.25 vs. 27.74 ms), and all seven configurations fall between 27.7 and 35.4 ms. The cost shows up under concurrent load: with 100 clients, Hybrid-512's mean latency was 50.9% higher than ML-KEM-768's. The concurrency results come from one trial per configuration at each load level, with every client connecting at the same instant, so they indicate direction rather than precise effect sizes.

The adaptive selector reduced mean latency by 27.3% and 99th-percentile latency by 17.3% relative to static Hybrid-512 in the evaluated high-concurrency settings, while choosing only among configurations that include ML-KEM.
